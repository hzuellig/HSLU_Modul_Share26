Tailwind mit Node — Architektur & eigenes Setup

Der Play-CDN aus Teil 2 war nur zum Reinschnuppern gedacht. Jetzt bauen wir ein echtes Tailwind-Projekt mit Node.js: eine feste dist/main.css-Datei, die nur die wirklich verwendeten Klassen enthält — und ein Watcher, der sie bei jedem Speichern automatisch neu erzeugt.

1. Warum reicht der Play-CDN nicht mehr?

Erinnerung aus Teil 2: der Play-CDN kompiliert bei jedem Seitenaufruf im Browser neu und liefert nie exakt die Klassen, die man später wirklich braucht. Für ein echtes Projekt will man stattdessen eine fertige, kleine CSS-Datei, die einmal — oder automatisch bei jeder Änderung — auf dem eigenen Rechner gebaut wird. Dafür braucht es Node.js: eine JavaScript-Laufzeitumgebung ausserhalb des Browsers, mit der sich genau dieser Bauprozess ausführen lässt.

2. Die Architektur: vom HTML zur fertigen CSS-Datei

Drei Werkzeuge arbeiten dabei zusammen: npm installiert und verwaltet sie, Tailwind generiert die Utility-Klassen, PostCSS reicht das Ergebnis durch eine kleine Pipeline weiter (Was ist PostCSS). Der Ablauf sieht so aus:

Quelle index.html

Enthält die Tailwind-Klassen im Markup, z.B. md:grid-cols-3.

→
Scan Tailwind Engine

Durchsucht die in content (tailwind.config.js) angegebenen Dateien nach benutzten Klassennamen.

→
Build PostCSS-Pipeline

Tailwind selbst ist ein PostCSS-Plugin. Zusätzlich: autoprefixer, ggf. cssnano zum Verkleinern.

→
Ergebnis dist/main.css

Enthält nur die Basis-Styles + genau die Klassen, die im HTML tatsächlich vorkommen.

Diese fertige Datei wird ganz normal per <link rel="stylesheet"> im HTML eingebunden — kein <script>-Tag zur Laufzeit mehr nötig.

3. Der Watcher: automatisch neu bauen bei jeder Änderung

Warum reicht "einmal bauen" nicht?

Während der Entwicklung ändert man laufend Klassen im HTML. Ohne Watcher müsste man nach jeder Änderung von Hand den Build-Befehl neu ausführen. Ein Watcher beobachtet die Quelldateien im Hintergrund und stösst den Build automatisch an, sobald sich etwas ändert — man muss nur speichern und den Browser aktualisieren (oder Live Server macht auch das automatisch).

4. Ein eigenes Projekt aufsetzen — Schritt für Schritt

01

Projektordner TestTailwindp5 anlegen + npm initialisieren

Legt eine package.json an, die alle Abhängigkeiten und Skripte des Projekts verwaltet.

npm init -y
02

Tailwind & PostCSS installieren

Werden lokal im Projekt installiert (Ordner node_modules/), nicht global auf dem Rechner.

Wichtig: npm install -D tailwindcss installiert ohne Zusatz mittlerweile Version 4, die eine andere Architektur hat (keine tailwind.config.js, kein postcss-cli nötig, CSS-basierte Konfiguration). Diese Anleitung — und das Designsystem in Teil 4 — basiert noch auf Version 3.4.14. Deshalb die Version explizit anhängen:

npm install -D tailwindcss@3.4.14 postcss postcss-cli autoprefixer
03

Config-Dateien erzeugen

Erstellt tailwind.config.js mit Grundgerüst.

npx tailwindcss init
tailwind.config.js — anpassen:
module.exports = {
  content: ['./index.html'],
  theme: { extend: {} },
  plugins: [],
}
postcss.config.js — neu anlegen:
module.exports = {
  plugins: {
    tailwindcss: {},
    autoprefixer: {},
  },
}
04

Input-CSS-Datei anlegen

Diese drei Zeilen ziehen die Tailwind-Layer (Grundreset, Komponenten, Utilities) in die eigene CSS-Datei.

css/input.css:
@tailwind base;
@tailwind components;
@tailwind utilities;
05

Build- & Watch-Skripte in package.json

Zwei Varianten: einmal bauen, oder dauerhaft beobachten.

"scripts": {
  "build-css": "postcss css/input.css -o dist/main.css",
  "watch-css": "postcss css/input.css -o dist/main.css --watch"
}
npm run watch-css
06

CSS im HTML einbinden

Ab jetzt einfach index.html speichern — der Watcher baut dist/main.css automatisch neu.

<link rel="stylesheet" href="dist/main.css">
Zum Ausprobieren
  • Führt die Schritte oben in einem leeren Ordner aus und startet npm run watch-css.
  • Öffnet index.html mit Live Server, fügt eine Klasse wie bg-red-600 hinzu und speichert.
  • Schaut euch dist/main.css an — die neue Klasse taucht dort automatisch auf.

6. Kombination mit p5.js im Instance Mode

Schreibweise wie sm:, hover: oder peer: noch unklar?

Bevor es weitergeht, lohnt sich ein Abstecher zur Tailwind-Basics-Seite — dort werden Breakpoint-Präfixe (sm:, lg:), Zustands-Präfixe (hover:) und peer/group separat und kompakt erklärt.

Das Setup ist nicht nur für Buttons und Boxen gedacht — genau dieselbe dist/main.css lässt sich auch neben einer p5-Sketch verwenden. Die Arbeitsteilung ist dabei klar: p5 zeichnet nur in seine eigene <canvas>, alles drumherum — Seitenlayout, Buttons, Cockpit-Leiste — bleibt ganz normales HTML und wird mit Tailwind-Klassen gestylt.

p5-Sketch (JS) Projekt laden sketch.js, Ball.js …

Instance Mode: function sketch(p) {...}, zeichnet ausschliesslich in das ihm übergebene Canvas-Element.

+
Tailwind (HTML) index.html

Klassen für Grid, Abstände, Buttons, Toggle — steuert alles ausserhalb des Canvas.

Die JS-Dateien der Sketches selbst enthalten keine Tailwind-Klassen — Tailwind muss sie deshalb auch nicht scannen. In tailwind.config.js genügt weiterhin content: ['./index.html'].

Mehrere Sketches responsiv gruppieren:
<div class="grid grid-cols-1 gap-6 sm:grid-cols-2 lg:grid-cols-3">
  <div id="canvas1" class="rounded-swiss border border-gray-200 bg-white p-4 shadow-sm"></div>
  <div id="canvas2" class="rounded-swiss border border-gray-200 bg-white p-4 shadow-sm"></div>
  <div id="canvas3" class="rounded-swiss border border-gray-200 bg-white p-4 shadow-sm"></div>
</div>

grid-cols-1 ist die Grundeinstellung für schmale Bildschirme (ein Sketch pro Zeile). Ab der sm-Breakpoint (≥ 640px) springt das Layout auf zwei Spalten, ab lg (≥ 1024px) auf drei — ganz ohne eigene Media Queries. rounded-swiss ist kein Standard-Tailwind-Wert, sondern kommt aus einer eigenen Theme-Erweiterung (siehe unten).

Woher kommen swiss-red, swiss-dark und rounded-swiss?

Diese Klassen sind kein Tailwind-Standard — sie stammen aus einer eigenen theme.extend-Erweiterung in tailwind.config.js: 

theme: {
  extend: {
    colors: {
      'swiss-red':  { 100: '#fae1e2', 500: '#e53940', 600: '#d8232a', 700: '#bf1f25' },
      'swiss-dark': { 500: '#46596b', 600: '#2f4356', 700: '#263645' },
    },
    borderRadius: { swiss: '0.1875rem' },
  },
}

Details, eine zweite Umsetzung als eigene Komponentenklasse und weitere Bausteine (Kopfbereich, Formulare, Schrift) stehen auf der Seite Swiss-Look nur mit Tailwind.

Buttons statt eigener CSS-Klasse .buttons:
<button id="button"
  class="inline-flex items-center rounded-swiss bg-swiss-red-600 px-4 py-2
         text-sm font-bold text-white shadow-sm transition-colors
         hover:bg-swiss-red-700 active:bg-swiss-red-800
         focus:outline-none focus:ring-2 focus:ring-swiss-red-500 focus:ring-offset-2">
  Click me
</button>

Statt einer .buttons-Regel in einer separaten CSS-Datei stehen Grundfarbe, Hover-, Active- und Fokus-Zustand direkt als Utility-Klassen im Markup — hover: greift beim Darüberfahren, active: während des Klicks (ein zusätzlicher, dunklerer Farbton, swiss-red-800). Ohne eigenes active: bleibt ein Button beim Klick optisch "stumm" — nur der Fokus-Ring erscheint, aber keine sichtbare Druck-Rückmeldung. Der zweite Button bekommt denselben Look als Outline-Variante (border border-swiss-red-600 text-swiss-red-600 statt bg-swiss-red-600), ohne eine zweite CSS-Klasse zu definieren.

Toggle-Switch mit peer/peer-checked statt eigenem CSS:
<input type="checkbox" id="checkboxInput" class="peer hidden" />
<label for="checkboxInput"
  class="relative flex h-7 w-12 cursor-pointer items-center rounded-full
         bg-gray-400 transition-colors duration-200 peer-checked:bg-swiss-red-600
         after:absolute after:left-1 after:h-4 after:w-4 after:rounded-full
         after:bg-white after:shadow after:transition-transform after:duration-200
         peer-checked:after:translate-x-5">
</label>

Die Original-Vorlage (p5_instanceMode/) löst denselben Toggle-Switch mit einer eigenen CSS-Regel #checkboxInput:checked + .toggleSwitch::after — der bewegliche Punkt ist dort ein ::after-Pseudo-Element des Labels, kein eigenes verschachteltes Element. Das ist kein Zufall: peer-checked:* erzeugt im Hintergrund einen Geschwister-Selektor (~) und wirkt deshalb nur auf echte Geschwister von .peer — ein verschachtelter <span> innerhalb des Labels wäre ein Nachfahre, kein Geschwister, und peer-checked:translate-x-5 darauf würde nie greifen. Tailwinds after:-Variante bildet deshalb genau das CSS-Original nach: sie stylt das ::after-Pseudo-Element des Labels selbst, das ist ein Geschwister von .peer — ganz ohne eigene CSS-Regel.

Zum Ausprobieren
  • Kopiert die Dateien aus p5_instanceMode/ Projekt laden (p5.min.js, Ball.js, sketch.js, sketch2.js, sketch3.js) unverändert in einen eigenen js/-Ordner.
  • Ergänzt theme.extend in eurer tailwind.config.js wie oben gezeigt.
  • Bindet die Sketches wie gewohnt per <script> ein und platziert die drei canvas-Container im responsiven Grid oben.
  • Ändert lg:grid-cols-3 testweise auf lg:grid-cols-2 und beobachtet, ab welcher Fensterbreite sich das Layout umbricht.

In den Header kopieren: Look and Feel BAG, :hover und :active Effekte des Hauptmenüs.
