Designsystem + Tailwind

Teil 3 hat ein generisches Tailwind+Node-Setup gezeigt. Jetzt schauen wir ein reales Beispiel an: designsystem_mini/ im Workshop-Repo — dasselbe Prinzip, aber mit dem Design System for the Swiss Confederation als Quelle für CSS-Klassen und Design-Tokens.

1. Lokal aufsetzen

Gleiche Befehle wie in Teil 3 — npm install lädt dieselben Werkzeuge (Tailwind, PostCSS, autoprefixer, …), nur mit einer umfangreicheren tailwind.config.js und mehr CSS-Quelldateien im Ordner css/.

cd designsystem_mini
npm install
npm run build-css
npm run watch-css

watch-css baut dist/main.css automatisch neu, sobald sich css/*.postcss, tailwind.config.js oder index.html ändert — genau der Watcher aus Teil 3, nur schon fertig konfiguriert. Öffnet index.html am besten mit der VS-Code-Erweiterung Live Server (Rechtsklick → "Open with Live Server").

2. Ordnerstruktur

index.htmlHauptseite: section/container/grid-Beispiele
css/Designsystem-Quellen (PostCSS), unverändert aus github.com/swiss/designsystem
tailwind.config.jsTailwind-Theme des Designsystems (Farben, Screens, Radien, …)
postcss.config.jsPipeline: postcss-import, tailwindcss, autoprefixer, cssnano
dist/main.cssgenerierte CSS-Datei (durch npm run build-css)
assets/logos/Logo Schweizerische Eidgenossenschaft

3. Was kommt von Tailwind, was vom Designsystem?

Wichtige Unterscheidung: Tailwind liefert nur die generischen Bausteine — Utility-Klassen, Build-Pipeline, Config-Format. Alle Klassennamen und Design-Entscheidungen, die im HTML zu sehen sind (container, card, top-bar, grid--responsive-cols-2, …), stammen aus dem Swiss Confederation Designsystem.

Direkt von Tailwind (generisch)

  • tailwindcss, tailwindcss/nesting als PostCSS-Plugins
  • postcss-import, autoprefixer, cssnano — Standard-Werkzeuge jeder CSS-Build-Pipeline
  • @import 'tailwindcss/base' etc. in main.postcss
  • Config-Grundstruktur (content, theme, corePlugins)
  • jede Utility-Klasse wie flex, p-4, md:inline

Vom Designsystem (projektspezifisch)

  • css/skins/*.postcss — Farbthemen als CSS-Variablen
  • css/foundations/*.postcss — Icons, Typografie, Spacings, Colors
  • css/layouts/*.postcss — container, grid--responsive-cols-*, section
  • css/components/*.postcss — btn, card, accordion, …
  • Werte in theme von tailwind.config.js (Farben als var(--color-primary-500), Screens, Radien) — die eigentlichen Design-Tokens des Bundes

Kurz: Ordnerstruktur, Klassennamen und Design-Tokens → Designsystem. Build-Mechanik und Utility-Prinzip → Tailwind.

4. Die wichtigsten Layout-Klassen

  • .section / .section--default — steuert vertikale Abstände
  • .container — steuert horizontale Abstände + maximale Breite
  • .container--grid — macht aus .container ein 12-Spalten-Grid
  • .container__full, .container__center--xs/sm/md — Platzierung im 12-Spalten-Grid
  • .grid--responsive-cols-2/3/4 — 1 Spalte mobil, mehr Spalten ab grösseren Breakpoints
  • .grid--responsive-cols-1/3-2/3 — feste Spaltenverhältnisse, z.B. für Sidebar-Layouts
  • .gap--responsive — Abstand zwischen Grid-Elementen, wächst mit dem Breakpoint

Alle Komponenten-Klassen (btn, card, input, navbar, accordion, table, badge, …) stehen unverändert zur Verfügung — Details in der offiziellen Doku.

Zum Ausprobieren
  • Öffnet designsystem_mini/index.html mit Live Server, bei laufendem watch-css.
  • Ändert eine Box von grid--responsive-cols-2 auf grid--responsive-cols-3 und beobachtet den Effekt beim Verkleinern des Fensters.
  • Sucht in css/components/btn.postcss nach der Definition von .btn und vergleicht sie mit einer reinen Tailwind-Utility-Klasse wie p-4.
  • Tauscht das Farbthema, indem ihr in index.html die Skin-Klasse wechselt (default / intranet / freebrand), und beobachtet, was sich ändert.
Mitnahme aus Teil 4 Du kannst in einem realen Projekt unterscheiden, was von Tailwind stammt und was vom Designsystem, und weisst, mit welchen Klassen sich responsive Layouts darüber bauen lassen.
